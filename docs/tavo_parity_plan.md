# Tavo 全功能兼容插件开发方案

本文档定义 Loyea 酒馆兼容插件对齐 Tavo（不含 Tavo 生态插件）全功能的开发目标、差距清单、阶段计划与工作规约。它是 [`tavern_plugin_refactor.md`](tavern_plugin_refactor.md) 的后续执行方案：重构已建立运行时可拔插骨架，本方案负责补齐 Tavo 功能差距并完成物理拆分收尾。

## 1. 目标与范围

### 1.1 目标

把 Tavo 功能与原生 Loyea 生态分离，做成 Loyea 的即时插件（现有 `:plugins:tavern-*` 模块族），并让该插件完整覆盖 Tavo 官方文档定义的全部功能面。验收口径：**一个 Tavo 用户携带其角色卡、预设、世界书、正则与聊天记录迁移到 Loyea 后，全部日常工作流可不降级复刻。**

### 1.2 明确排除

- **Tavo 生态插件**（第三方扩展体系）——不做复刻，保持 blocked/unsupported 诊断。
- **Volink 云服务**（Tavo 自家注册/计费/一键配置）——Loyea 使用用户自有 API 体系。
- **Tavo 品牌专属 UI 视觉**——对齐交互语义与信息结构，不复刻像素。

### 1.3 体积门禁（硬性规则）

任何阶段如需引入满足以下任一条件的依赖，必须**立即中断开发并向用户报告**，经确认后才可继续：

- 单个依赖 AAR/JAR 体积超过 1 MB；
- 任何需要捆绑原生库（.so）、独立运行时（如 JS 引擎、浏览器内核）或超过 2 MB 总增量的传递依赖闭包；
- 为实现某功能需要引入新的大型环境（如嵌入式数据库引擎、脚本虚拟机）。

当前评估：本方案全部任务均可在现有依赖（OkHttp、Gson、Compose、WorkManager）内完成，无预期新增依赖。唯一风险点是 URL 导入若需解析第三方站点 API 格式，应仅用现有 HTTP 客户端 + JSON 解析实现。

基线来源：Tavo 官方文档（docs.tavoai.dev）角色、聊天、群聊、预设、历史、API 设置各页。对照结论分四档：✅ 已达标、➕ 超出 Tavo、◐ 部分达标、❌ 缺失。

### 2.6 预设（Preset）

| Tavo 功能 | 现状 | 说明 |
| :--- | :--- | :--- |
| 导入 SillyTavern 预设 | ➕ | 全 prompt_order/trigger/深度语义 |
| 预设运行时（全部详细槽位） | ➕ | Tavo 文档列的 17 个槽位均在 Prompt Manager 模型内 |
| **应用内预设创建/基础提示词编辑器** | ❌ | 只能导入，无内置编辑 UI |

### 2.7 超出 Tavo 的既有能力（不需回退，仅登记）

Quick Reply v2 + 安全 STscript、宏引擎（嵌套/条件/时间/随机种子冻结）、Continue/Swipe/Impersonate 全链路、Branch/Checkpoint、Author's Note、World Info ST v2 全字段（递归/预算/sticky/cooldown/深度 role）、CHARX 导出。这些保持现有门禁，不纳入本方案回归范围。

### 2.8 落在原生层的对齐项（不进插件，登记决策）

以下能力属于通用聊天宿主而非"酒馆兼容语义"，按现有架构原则放宿主实现，但交互语义对齐 Tavo：会话级 API 切换、会话置顶/克隆/重启/过滤/统计的存储与 UI、长期记忆开关、聊天主题定制（Loyea 已有主题系统，会话级主题切换列入原生路线图，**不属于本插件验收**）、TTS（Loyea 原生 TTS 已超出 Tavo 指南范围）。

> 边界判据：凡"角色卡/预设/世界书/正则/群聊语义/JSONL 数据格式"归插件；凡"任何聊天应用都需要的基础设施"归宿主，由 `plugin-api` 契约解耦。Tavo 用户的完整工作流由"宿主基础能力 + 插件语义层"共同满足。

## 3. 差距任务清单

按落点模块归组，每项任务标注：落点、类型（纯核心 / 宿主桥接 / UI）、验收依赖。

### A. tavern-core 纯核心（无 Android 依赖）

| # | 任务 | 说明 | 验收 |

| A1 | 会话统计计算器 | 输入会话消息流 → 输出陪伴天数（首条消息至今）、双方消息数、总字数；口径与 Tavo 统计页对齐 | JVM 单测：空会话/跨年/仅系统消息 |

## 4. 阶段计划与顺序决策

**先功能后拆分的理由**：D2（CharacterCard 拆分）会重排数据模型，若先拆后加功能会二次迁移；功能补齐大部分落在纯核心层（A 组）与独立宿主能力（B 组），与现有结构正交，稳定后再做一次性物理搬移，避免"边搬边改"。

```text
Phase 1  Tavo 功能补齐（A1-A4 → B1-B7 → C1-C2）
          ├─ 批次 1.1：A 组纯核心（tavern-core，全 JVM 单测）
          ├─ 批次 1.2：B 组宿主桥接（每任务独立提交+受影响模块测试）
          └─ 批次 1.3：C 组预设编辑器
          出口条件：§2 差距表中所有 ❌/◐ 变 ✅/➕，fixture 全绿
Phase 2  物理拆分收尾（D1 → D2 → D3 → D4，沿用既定顺序与门禁）
          出口条件：tavern_plugin_refactor.md "尚未完成的物理拆分"清零
Phase 3  全案验收
          ├─ fixture 回归：全部模块测试 + 依赖方向门禁
          ├─ 真机人工清单：URL 导入 / 统计 / 克隆重启 / 会话 API 切换 / 群聊选角 API / 预设编辑器 / 插件热插拔 / 旧数据迁移
          └─ 迁移演练：真实 Tavo 导出物（角色卡 + jsonl + 预设 + 正则）导入全流程
```

每批次出口才跑一次全量门禁（见 §7）；批次内仅跑受影响模块。

## 5. 架构原则（不变项）

1. 模块依赖方向维持 `app → plugin-* / knowledge-core / tavern-*`，核心 API 与中立知识模块不依赖 Tavern 实现。
2. 网络下载、SAF、分享、通知等副作用一律由宿主端口提供；tavern-core 只产出纯数据变换与请求模板（A3 即此模式）。
3. 会话/消息存储仍由宿主持有；插件通过 `PersonaProjection`/冻结回合/lease 契约交互，B 组新能力不破坏该边界。
4. 新增会话元数据字段（`apiBindingId`、`memoryEnabled`）必须有默认值迁移与原始备份，沿用 `pre_persona_binding_v1.json` 的迁移纪律。
5. 所有 Tavo 语义对齐项绑定官方文档 URL + 输入 fixture + 请求快照断言，不接受"字段能读写"当作兼容。

## 6. 开发工作流规约（成本控制，强制）

吸取 2026-08-24 Codex 马拉松事故（单一会话 6 个用户回合滚出 2.48 亿 input tokens）的教训：

1. **一任务一会话**：每个编号任务（A1…D4）独立会话/子代理执行，带本方案对应章节 + 现状代码摘要开工；禁止跨任务续跑长会话。
2. **重活用子代理**：文件搬移、批量改写、全量测试运行交给子代理/fork，主会话只做规划与验收，避免上下文雪球。
3. **测试分级**：
   - 日常：仅受影响模块（如 `:plugins:tavern-core:test --tests "*Statistics*"`）；
   - 批次出口：该批次触及模块全集；
   - Phase 出口：§7 全量门禁。
4. **大文件纪律**：ChatViewModel.kt / ChatScreen.kt 等超千行文件按需分片读取，读完即用，不整文件进上下文；优先用 grep 定位。
5. **DoD 前置**：每个任务开工前写清完成定义（验收列），不满足不提交；满足即提交并结束该会话。
6. **中断规则**：触发 §1.3 体积门禁、遇到需要破坏性数据迁移、或单任务连续超过 2 小时未出现绿色测试，立即停下向用户汇报。
